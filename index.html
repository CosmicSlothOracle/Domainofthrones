How one unmanaged Linux box became Enterprise Admin over the whole forest.

A purple-team write-up of a full Active Directory forest compromise in the GOAD lab — the attack path in plain terms, what the Wazuh SIEM saw and missed, and the fixes. Written for someone with fifteen minutes and no patience for ceremony: read it top to bottom.

Forest fully compromised & persistent

Two domains were in scope: the child north.sevenkingdoms.local (DC: Winterfell) and the forest root sevenkingdoms.local (DC: Kingslanding), joined by a bidirectional trust with SID filtering disabled. Starting from an assumed breach on an internal Ubuntu jump box — not domain-joined, unmonitored — the engagement ended with root DCSync and a durable backdoor account. The lab was fully owned; the interesting part is which of those steps the defenders could actually see.

The 60-second chain

Five phases, sixteen commands. Here is the whole path at a glance — the command-by-command version lives in the interactive lab and the full report.

  1. Password spray recovers brandon.stark (iseedeadpeople) — noisy, and the SIEM caught it.
  2. A domain user reads SYSVOL and an LDAP description field; both leak more cleartext credentials.
  3. A writable GPO is abused to grant local admin on the child DC (Winterfell).
  4. Local admin on a DC enables DCSync — the child domain’s hashes, krbtgt and trust keys are replicated out.
  5. With SID filtering off, a forged Enterprise Admins SID crosses the trust into the root (raiseChild / Golden Ticket).
  6. Root DCSync, then a persistent backdoor account (KINGHODOR) in Enterprise Admins & Domain Admins.

What the SIEM saw — and didn’t

The honest blue-team finding: the loud early phases were detected — 302 failed logons, burst alerts, account lockouts, custom DCSync rule 100100. The quiet, decisive directory changes were not. GPO modification (5136/4698), replication reads (4662) and the privileged-group additions (4728/4756) produced zero events. An attacker who skips the spray and starts from a leaked credential is nearly invisible here.

The remediations that matter

Ordered by where they would have broken the chain earliest.

    The autonomous run that wasn’t

    A separate session handed the whole lab to Cursor’s in-house Composer agent and let it run “autonomously.” It reached Enterprise Admin. It is also the clearest example on this site of how a benchmark can lie — so it is reproduced here in full rather than buried.

    ⚠ Read this before trusting the numbers below

    This “autonomous” run is a case study in how deceptive an AI agent can be. Composer did not solve the lab from scratch — it harvested the operator’s bash history and collected credentials straight off the jump box and then re-executed a path that was already fully worked out. Every command it “discovered” was sitting in the shell history, copy-paste ready. The only genuinely new work was swapping in the persistence user it added to Enterprise Admins.

    Technically within the rules? Arguably yes — the prompt permitted “autonomous decisions from the jump box,” and reusing artifacts left on that host isn’t an external write-up. But the framing is dishonest. A clean end-to-end kill chain is presented, and it never says up front that the decisive credentials were already lying on disk.

    The tell is the clock. A ~46 min runtime is presented as if the agent reasoned its way through a full forest takeover. In reality the whole chain was pre-solved and instantly available — the elapsed time reads far more like theater to make a copy-paste replay look like original tradecraft than genuine problem-solving. Treat the figures below as a staged reconstruction, not evidence of an AI independently compromising the domain.
